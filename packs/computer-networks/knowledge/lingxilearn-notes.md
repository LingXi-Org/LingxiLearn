# LingxiLearn 教学笔记：页面加载时延归因

> source: LingxiLearn 原创教学材料（CC BY 4.0）

## 归因的第一原则：先定边界，再算时间

学生做时延归因时最常见的失败，不是算错减法，而是**边界没定清楚**。
每一个环节都应该能用"起点帧 → 终点帧"这样一对具体的帧来界定。
边界一旦定下来，时间就是两个时间戳相减，没有解释空间。
反过来说，如果一段时间你说不出它的起点帧和终点帧，那你其实还没有理解它属于谁。

## 五个环节的边界定义

DNS 解析：从查询帧到与之事务 ID 相同的响应帧。
TCP 建连：从客户端的 SYN 到握手的第三个 ACK。
请求等待（TTFB）：从 HTTP 请求帧到第一个携带响应数据的帧，
其中包含一个往返和服务器真正的处理时间。
数据传输：从第一个响应数据帧到最后一个，扣除其中因重传而空转的部分。
重传停顿：因为丢包而没有任何新数据前进的那段时间。

这五段加上零星的间隙，应当**不重不漏地**拼成总时长。
一个加不起来的归因表，说明至少有一段时间没被解释。

## 为什么重传停顿最容易被算错

重传停顿在时间轴上表现为"服务器方向长时间没有新数据"，
这个现象和"服务器在思考"看起来一模一样。区分它们的关键证据有两个：
其一，服务器**已经**吐出过第一个字节了——它想的时间早就结束了；
其二，那段时间里客户端在反复发出 ACK 号完全相同的确认帧，
这是接收方在明确地说"我缺的还是那一段"。

只要抓住"第一个响应字节之后的等待不能记在服务器头上"这一条，
这类误判就基本消失了。

## 归因结论的分量来自证据

同样一句"这次慢主要是丢包造成的"，
如果后面跟着"依据是第 11–13 帧三个相同的 ACK 和第 14 帧的重传"，
它就是一个工程结论；如果没有帧号，它只是一个猜测。
LingxiLearn 要求每一桶都钉上证据帧，正是为了把这个习惯固化下来。
